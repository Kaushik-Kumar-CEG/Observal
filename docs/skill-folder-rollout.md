# Registry-direct skill folders: maintenance rollout

**This is an operator runbook, not a release sign-off or a user-facing install guide.** The server can author bounded, versioned folders and conditionally return complete selected-version files, but this branch does not implement the CLI whole-folder installer or the web folder editor/version-keyed reviewer. Do **not** enable resource-bearing review/delivery or tell users that a returned manifest is an installed skill.

## Gate and compatibility

- `registry.skill_folder_delivery_enabled` defaults to `false`. While false, exact resource-bearing review and negotiated standalone/agent folder delivery return **409**. Old clients without `skill_extra_files_v1` still receive **409** for a selected resource-bearing release after the setting is enabled; Kiro/Cursor cannot receive skill folders. Ordinary resource-less and Git-fetch paths remain available.
- The setting does **not** disable author writes, legacy resource-less private→public transitions, or an old process that does not implement the new review markers. **Tracked skill visibility and ownership moves remain disabled while the setting is false.** On a deliberately enabled, homogeneous development fleet, these routes now lock and validate every saved version, rebind all content and draft-base revisions to the final identity, invalidate prior observations and requeue public approvals for exact global review. Corrupt revisions, stale draft bases or a transfer carrying unresolved prior team approval provenance return 409. This is a gated server development path, **not** a production rollout or proof of client filesystem safety. Older workers do not enforce the same transaction; the setting is not a mixed-fleet safety barrier. Never run a mixed old/new API or worker fleet against resource-bearing data or public-skill re-review. This is a **maintenance-window deployment**, not a rolling migration. Do not turn the setting on until the compatible CLI staged installer, reviewer UI, capability negotiation and human review are complete.
- Concrete standalone and pinned-agent install request/response examples, including binary bytes, an executable file, v2 digest, lock checksum and exact refusal messages, are in `tests/fixtures/skill_folder_install_contract.json`; author/review requests are in `tests/fixtures/skill_folder_contract.json`. These are **server responses**, not evidence of a safe filesystem installation. Both fixtures are schema-checked; old-client refusal and binary delivery are also exercised through actual HTTP routes.

## Planned self-hosted Compose sequence

Use the exact Compose files, profiles, project name and replica count from **your deployment** (`docker/docker-compose.yml`, any production/observability overrides, or `docker/server-package/docker-compose.yml`). The placeholders below are not a universal copy-and-paste invocation.

1. Schedule downtime. Take and verify a PostgreSQL backup and preserve package, Compose config and secrets; record the running API/worker image digests. Include ClickHouse in the site's recovery plan. Test restoring backups separately; retaining a binary does **not** roll back a database.
2. Drain/stop ingress (`observal-lb`), then **all** old `observal-api` and `observal-worker` replicas, including separately scheduled or remote processes. Use `docker compose ... stop observal-lb observal-api observal-worker` with your actual Compose options. These services use `restart: unless-stopped`: verify `docker compose ... ps -a` and prevent external orchestrators from reviving old workers. Keep PostgreSQL, ClickHouse and Redis running. Do not perform a rolling `up -d` during the schema change.
3. After confirming **zero** old API/worker processes, stage the homogeneous new image and run **one** `observal-init`. Require exit status zero, inspect the PostgreSQL `alembic_version` row (head on this branch: `036_discovery_trgm`), and verify ClickHouse migrations completed. The init entrypoint creates model tables and stamps **only** an actually empty schema after creation succeeds; a versioned schema runs Alembic upgrade; existing unversioned tables refuse automatic repair. Failed upgrades exit nonzero before ClickHouse and do not falsely stamp head.
4. If initialization fails, leave ingress and workers stopped. Inspect the recorded schema state and restore the tested pre-upgrade database snapshot when necessary **before** starting an old binary; do not manually stamp unknown tables or assume package restoration reverses data/schema changes.
5. Start new API and workers from the same image digest; verify health and existing resource-less behavior before restoring ingress. Keep the folder setting `false` until the compatible CLI and web workflows and selected-version HTTP/filesystem checks have passed on every supported harness. Only then may an administrator set the DB dynamic setting via the enterprise settings workflow (`PUT /api/v1/admin/settings/registry.skill_folder_delivery_enabled`, JSON body `{"value":"true"}`). Explicitly refresh/restart every process's settings cache and independently check all replicas; a DB write does not prove every worker has observed the new value.

For package installs, `install-server.sh` unpacks into a sibling staging directory and retains the old package/config/secrets in `<install-dir>.backups/`. An ordinary setup failure attempts to restore previous *binary files*, retaining failed bytes for inspection. An interrupted upgrade leaves `<install-dir>.upgrade-in-progress`: inspect the backup and restore deliberately before clearing the marker. Do **not** restart a previous binary on a newly migrated DB without a verified DB restore. These behaviors were tested with local archives, **not** live Compose/container recovery.

## Evidence and remaining release checks

A disposable PostgreSQL database passed the packaged entrypoint on an empty schema and repeat start at head 036, an empty-data downgrade to 032 and re-upgrade, failure without false head stamp, and interrupted unversioned-schema refusal. A populated skill release refused destructive 033 (review attribution), 031 (review epoch), 030 (draft/review provenance) and 029 (stored files) downgrades without changing the revision; only after **deliberately clearing disposable test data** did downgrade to 028 and re-upgrade pass. This is **not** a production downgrade procedure. Migration `020_remove_legacy_scope` explicitly prevents a full downgrade to `v1_baseline`.

A real stopped pre-feature PostgreSQL 18 volume was copied **read-only** to a disposable networkless clone. Crash recovery occurred only in that copy. A restricted custom-format dump at revision 027 restored successfully into separate databases; one copy upgraded 027→036 with release identity and content bytes unchanged, and the exact old API image read another restored 027 database. Comparing schema-only dumps of that upgraded database and a fresh stamped 036 model found only physical column ordering, an equivalent team check-constraint expression, and pg_dump's random restrict marker. The absent historical discovery trigram index was repaired by 036. This verifies **one specific pre-feature snapshot**, not every deployed database or a full old API/worker restart with Redis and ClickHouse. A separate synthetic-credential Compose project passed fresh/repeat init, healthy API/worker, deliberate failed migration, database snapshot restore and healthy restart at 036. The original services were not part of those upgrade rehearsals. After a separate operator-approved recovery, the stopped PostgreSQL, Redis and ClickHouse containers were restarted **on their old, unchanged revision 027**; the old API/worker image and ingress then passed health checks with folder delivery still disabled. No new binary or migration was deployed to the original stack. This is not evidence of a new-code production rollout. Remaining release prerequisites include compatible CLI/web workflows, real staged filesystem installs, an independently reviewed complete diff and human sign-off. Leave the setting `false` after any failed migration or compatibility check; never claim OS-level crash atomicity or safe mixed-worker serving.
