# Registry-direct skill folders: maintenance rollout (not a release sign-off)

**Do not enable `registry.skill_folder_delivery_enabled` on a mixed fleet.** It defaults to `false`. While false, exact resource-bearing review and negotiated standalone/agent delivery return 409. Old clients without `skill_extra_files_v1` remain unable to install resource-bearing versions even after enabling it. The switch does *not* disable author writes or protect an old process that does not know about it; admission control for resource uploads and private→public transitions requires stopping **every** old API and job worker, not merely switching a setting on one new replica. Release remains blocked until the complete CLI installer, reviewer UX, homogeneous-worker rollout and populated-schema downgrade are validated.

For a self-hosted Compose installation, first snapshot PostgreSQL and the complete package/config/secrets and record the currently running image digests. Schedule downtime. Stop ingress (`observal-lb`), then all `observal-api` and `observal-worker` replicas with the **exact Compose files and profiles** used for this deployment (`docker compose ... stop observal-lb observal-api observal-worker`). `unless-stopped` is present: verify `docker compose ... ps -a`, any separately scheduled workers, and any remote replicas remain stopped; prevent external orchestrators from restarting old containers. Keep DB, ClickHouse and Redis running. Do not use rolling `up -d` during schema changes.

Only after observing zero old API/worker processes, stage the new homogeneous image, run **one** `observal-init` invocation and inspect its exit code and Alembic revision (`033_skill_private_review` for this branch). The init container stamps only after transactional schema creation on a genuinely empty database; an existing versioned database runs Alembic upgrade, and an unversioned database with tables refuses both paths. A failed upgrade exits nonzero and never stamps head: leave ingress/workers stopped, inspect DB state and restore from a tested pre-upgrade snapshot when required. Do not manually stamp an unknown existing schema or assume a previous binary can read a migrated database. Verify ClickHouse migration completion too. Start new API and workers from the same image digest, health-check and test resource-less functionality, then restore ingress. Do not enable resource-bearing review/delivery until the full-file CLI installer, web reviewer and explicit versioned-client negotiation are deployed and exercised on every supported harness. Set the DB dynamic setting through the enterprise/admin settings workflow only after these checks; restart/refresh all workers' settings caches and independently verify all instances see the same value.

**Verification and remaining blockers:** `v1_baseline` is a no-op, so the packaged init now creates current-model tables only when the PostgreSQL schema is genuinely empty, then records the revision. A disposable empty PostgreSQL database passed this exact entrypoint twice, then passed the versioned 032→033 upgrade after reconstructing the preceding columns. The shortened `033_skill_private_review` revision fits the standard 32-character Alembic column. An interrupted fresh create/stamp is deliberately left unversioned for manual inspection, not guessed to be complete. The known migration-created ARD trigram index and named skill-review foreign keys now exist in the model-built fresh schema and are asserted in the PostgreSQL rehearsal; a full historical DDL audit is still required before general release. `install-server.sh` now unpacks into a sibling stage, retains the previous package/config/secrets under `<install-dir>.backups/`, and attempts ordinary-failure restoration of the previous binary while retaining failed bytes. An interrupted upgrade leaves `<install-dir>.upgrade-in-progress`; inspect the backup and restore explicitly before removing the marker. These guarantees were tested with local archives, **not** live container swaps: setup may already have changed the database, and neither the binary backup nor re-running setup downgrades it. Do not restart an old binary on a newly migrated schema without a separately verified DB restore. Populated downgrade guards still require deliberate data handling; a full downgrade to `v1_baseline` is unsupported because migration `020_remove_legacy_scope` is explicitly irreversible. Keep the setting false and traffic drained on any failed migration or compatibility check.
