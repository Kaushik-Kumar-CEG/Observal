## Data, auth and disclosure boundaries retained

Only **subject UUID bookmarks** sync under `(immutable server UUID, server-provided project ID, viewer UUID, cohort)`. Global `1w|1m|3m` period and visibility selection, selected API/browser origin, theme, tokens, device IDs, cached counts and local pending intents are **device-local**. Never store/transmit names, email, roles, component IDs, activity or trace in bookmarks. A follow grants **no** Author/User or private-person visibility; `/mobile-activity/v1/people/resolve` still controls public identity and the default-closed person-read barrier. A removed/unavailable UUID reveals only a generic unavailable entry to its owner, not stale profile data. New follows must lock and verify public/live subject eligibility; subject erasure transactionally purges UUIDs from **all** owners, invalidates old cursors/change checkpoints via a non-identifying erasure floor and fences re-adds. Account/DSR deletion purges bookmarks, generation/high-water, approvals, consent, dedup and audit references that could reconstruct follows. Logs contain only counts/IDs unrelated to followed subjects.

Opt-in disclosure states that this server stores private account follows across separately approved phones; phone unlink/logout does **not** erase account follows, while **remove-all** and **withdraw account consent** are distinct explicitly confirmed actions. Every mobile route rechecks current server/project/cohort, account/device/revocation/SCIM, Redis and privacy barrier; browser/desktop routes recheck current owner, server/project/cohort and account revocation without inventing a mobile device. `mobile:read` stays exact accepted v1.2; it cannot directly modify follows or grant general API write. A phone calls `/write-authorization` for a ≤600s code bound to owner/device/**current generation**; accepting remove-all or withdrawal invalidates **unapproved challenges too**, so an old code cannot create a fresh approval after re-consent. Browser approval of an outdated challenge returns 409 generation_conflict. The phone calls for a new code after any generation change; the same-account human independently signs in at the genuine issuing-server browser and approves **this device's** follow-write scope using normal browser JWT, never the mobile bearer. `/write-grant` also requires still-valid consent, approval and owner generation; returns separate `aud=observal-mobile-follow-sync-v1`, `scope=mobile:follow-write`, unrefreshable ≤300s JWT bound to account/device/cohort/generation and checked against authoritative DB **on every write**. A stolen unapproved mobile read JWT cannot bootstrap write. Logout/unlink/SCIM/revoke/withdraw/removal invalidate approval and old write JWTs before expiry. No token in a browser redirect; actual `/device` SPA JS and same issuing server must later be proven on an authorized instance. Accepted `/auth/device/token`, `/auth/token/refresh`, `/auth/mobile/credential` wire is unchanged.

## Negotiation, old servers, bounds and losslessness

After **fresh same-issuer v1.2 mobile credential and capabilities proof**, call only `GET /mobile-follow-sync/v1/availability`. A strict JSON 200 must contain exact `version=1.0.2`, server/project/viewer/cohort and `owner_generation`, state `available|disabled|consent_required|restricted|withdrawal_pending`, max page 100, offline horizon 30. Only a **404 or 405 from THIS availability URL** after that fresh v1.2 proof (even older server's non-JSON body) means **Local follows only — sync unavailable**, preserving v1.2 activity; it is **not** an empty synced snapshot. Never treat 401/403/503/429, an HTML 200, unknown/newer version, 3xx or different-issuer/mismatched-origin response as extension absence; deny, lock local cleartext and retain encrypted same-account pending intent. Do not redirect an authenticated API token. Older apps make no new request. A selected v1.2-valid API origin longer than 512 characters does not qualify for this extension (403 `restricted`, without echo), while v1.2 activity remains intact. Servers whose v1.2-valid project ID exceeds the proposed 256-character sync response bound return 403 `unsupported_project` **without echo** and remain v1.2-only, not an old-server 404.

Every owner generation, global/person revision, change ordinal, after/base revision and removal revision is an **exact JSON integer in 0..9,007,199,254,740,991** (generations and committed revisions ≥1). Signed cursor characters ≤1,300 and sync-supported canonical HTTPS API origin ≤512 (the longest full `/changes` URL including generation/revision/limit fits under 2,048); complete URL ≤2,048, browser origin ≤512, project ID ≤256 in sync responses, error enum ≤64, page ≤100, request body ≤4,096 UTF-8 bytes before JSON parsing; no subject UUID in an ordinary error. Query numeric values use only canonical unsigned base-ten characters (`0` or nonzero no-leading-zero, no `+`, exponent, decimal point or whitespace); server rejects numbers above JS MAX_SAFE_INTEGER **before** converting to any lossy Number. Server checks every increment atomically: at max return `409 revision_exhausted` (or 400 for out-of-range input), never round, wrap, reset across an active generation or silently compare imprecise values. Existing signed cursors carry integer values within the same bound and are verified server-side. A valid older-version response cannot be coerced into this shape. No implicit extension of 30-day original mobile refresh family.

## Generation, concurrency and explicit owner remove-all

An owner partition starts with `owner_generation=1`, monotonically advances under a serialized owner lock **before** any accepted account remove-all or withdrawal and **again on explicit re-consent**, never wraps. Every complete snapshot/export page, fixed-upper `/changes` page/cursor/checkpoint, pending intent/request, 90-day op record/outcome and ≤300s write JWT binds generation; availability and consent state publish it. `POST /operations` accepts **exactly one** conditional `{operation_id,subject_id,owner_generation,base_person_revision,action:follow|unfollow}`. Check the authoritative owner generation **first**, then the per-subject revision and active consent/approval under one transaction with insertion locks. Independent subjects commute; same subject first committed edit wins, second gets `409 person_conflict` with owner-submitted subject's current revision + following boolean. No batch/list overwrite or silent rebase. Duplicate same op ID/body in the *current* generation returns exactly the original 200 or 409 JSON/status for ≥90 days **only while that subject has not been erased**; erasure redacts the stored outcome and any same-generation POST replay returns `409 subject_erased` without UUID, never the old 200. Changed body returns `409 operation_id_reused`. Commit-before-200; 404 status means unknown, not no commit. Unfollowed subject retains minimal high-water until generation reset; loss of 90-day full tombstones never resets its revision *within that generation*. Client may use a conflict's revision/current_following for an absent bookmark only after fresh full snapshot and renewed explicit user intent with **new op ID**; no automatic old follow replay.

**Two-phone removal race:** Phone A queues a *never-before-followed* UUID with base=0, generation=7; phone B obtains ≤120s nonce bound to generation=7, explicitly confirms account-wide remove-all, and in one transaction the server increments to generation=8, sets durable pending fence and invalidates all old write JWTs and per-device browser approvals. An old op cannot apply after completion even though its UUID has never had a high-water row. An old/revoked generation-7 write JWT is **401** before inspecting its body; only a newly browser-approved generation-8 write JWT submitting the old request body receives `409 generation_conflict` with current generation and no private subject fields. Phone A MUST take a new 8-pinned full snapshot and **new browser-approved grant**, and show explicit human re-follow decision; if approved it creates a **new** ID/base=0/gen=8. Never transplant an old queued op's generation or reuse its ID. While pending/needs_operator, no edits or partial snapshot/changes/export; worker resumes idempotent ≤100-row batches under a durable cursor and audits failures. `GET /removals/{id}` returns `pending|needs_operator|completed`; only completed reopens reads (but no prior approval is restored). A lost 202 cannot be replayed with the now-revoked old write JWT (401). Instead `POST /removals/lookup` with the original `{nonce,original_owner_generation}` and a fresh authenticated **mobile:read from the same owner/device** returns the durable `RemovalState` (200) using a minimal 90-day nonce digest; unknown 404 is not proof of no commit, and the client retains the nonce locally until status is settled. This lookup never replays or bypasses write authority. A mismatched nonce/device/project is denied and no subject data is returned. A submitted removal cannot be canceled/reverted. `needs_operator` keeps fence until named audited repair/resume/reconciliation. Remove-all **does not withdraw consent**.

**Lost 200 / status across a generation change:** Retain only minimal `(owner,operation_id,original_generation,original_http_status,expiry)` for 90 days when removal/withdrawal erases subject/op payload. `GET /operations/{id}` returns 200 with `original_http_status`, `effective:false`, current `owner_generation`, and `{status:superseded,reason:owner_reset,original_owner_generation,owner_generation}` with **no subject UUID**. An old POST replay cannot regain its original 200 after generation advances: an old write bearer gets 401; only a valid **new-generation write bearer** carrying the prior request body gets `409 generation_conflict` and never writes. Android must show Superseded / Not synced, not Synced, even if original 200 arrived late. Status `effective:true` and original result only while the same generation remains, consent is active **and the subject was not erased**. Subject erasure redacts affected status IDs even without a generation change (`effective:false`, reason=`subject_erased`, no subject UUID), and denies old POST replay before any dedup result is returned. Strict Android parsing additionally checks an effective result's `owner_generation` equals top-level current generation; JSON Schema cannot enforce cross-field equality by itself and implementations must reject a mismatched result. Expired dedup returns 410; require fresh snapshot and explicit choice. The per-generation **proposed** capacity is ≤100,000 *distinct* subject UUIDs including removed high-water keys; at capacity new UUID gets `409 capacity_reached`, while unfollows/removal remain possible. **Unlike rejected 1.0.1's lifetime cap, completion of remove-all advances generation and releases all old high-water/quota storage, allowing future new follows after new approval.** No silent ceiling at 250. The actual default, storage/backup/DSR cost and legal consent basis are **pending named owner policy decision**; this proposed 100K figure is not a production-approved quota or a reason to enable sync.

## Explicit withdrawal, re-consent and cross-phone erasure

`POST /consent/withdraw` accepts either the current independently browser-approved owner/device **`mobile:follow-write`** grant (≤300s) OR an authenticated same-owner browser/desktop bearer with explicit account-wide confirmation. It does NOT accept `mobile:read`. A browser owner can withdraw even after unlinking/loss of the last phone; the browser bearer gains no follow-edit authority with `{confirm:true,owner_generation,withdrawal_id}` (one UUID for idempotent retries). This is an explicit disclosed **account-wide opt-out**, not logout and not remove-all. In the acceptance transaction increment owner generation, mark durable `pending`, invalidate **all** phones' browser approvals and current/old write JWT generations and deny queued edits; erase current follows, high-water, tombstones, dedup payloads and consent in restartable ≤100-row batches. Minimal non-identifying operation/removal/withdrawal ID+generation status for ≤90 days exists solely for lost-ACK recovery and must not reconstruct subjects. 202 `pending` is **never** success; `GET /consent/withdrawals/{id}` is available with a still-authorized `mobile:read` OR the same owner's browser/desktop bearer after write revocation and reports pending/needs_operator/completed. The browser can initiate and track withdrawal even when the last phone was unlinked or lost; neither session gains a follow edit permission. A replay using the revoked pre-withdrawal write bearer is 401, never a bypass; use the original withdrawal ID/status for lost-202 recovery. A duplicate withdrawal ID/body in a still-current generation is idempotent, a changed body is 409. If worker fails, `needs_operator` leaves reads/edits fenced until audited repair. After completed, availability=`consent_required`, snapshot/changes/export are denied, and status lookups may expose only owner-bound redacted supersession. Per-device old encrypted intents remain local but **may not be submitted**; no silent replay or transfer. Initial opt-in AND second-phone re-consent use a separate **same-issuer authenticated browser/desktop account bearer**, never `mobile:read`. Browser `GET /consent/state` obtains current generation/state without bookmarks; the product browser UI must present account-wide disclosure before explicitly submitting `POST /consent {consent:true,owner_generation,consent_id}`. A normal bearer cannot cryptographically attest that a human saw the page; desktop bearer automation could also call this route. The named owner must review this lawful-consent/UX boundary before enablement—do not claim server-enforced human presence. A phone's read grant cannot invoke that route (401), even if it fetched the new generation via availability. Consent advances to a new generation **only if state is `consent_required`, the supplied current owner generation matches and no withdrawal/removal is pending**. Already `available` with a new consent ID returns `409 consent_already_available` without changing generation or existing follows; a byte-identical retry of the previous successful ID/body returns its previous 200 only while that resulting generation remains active. Every `(owner,consent_id)` is bound to body/generation for 90 days; an identical lost-200 retry while the resulting generation is still active returns the original result, but a delayed pre-withdrawal opt-in or replay after any intervening generation change returns 409 `generation_conflict` without restoring consent. A `mobile:read` token alone cannot re-opt-in after withdrawal; current browser bearer, fresh browser-rendered disclosure, current generation and new ID are required. Human consent/legal-basis UX still requires separate named owner review. Then then **each** phone obtains its own fresh browser write approval/grant and full snapshot; any old intent requires new user choice and operation ID/gen/base. No deleted bookmarks reappear, even if a device was offline throughout withdrawal. Account deletion/subject erasure are separate stronger fences. An owner must decide lawful consent and unblock UX before implementation approval.

## Bounded reads, retention and progress

`GET /snapshot` and `/export` page ≤100 subject UUIDs pinned to generation and revision with signed ≤15-minute keyset cursor; concurrent writes do not starve progress because point-in-time versions last through cursor expiry. `GET /changes?owner_generation=G&after_revision=R` pins an inclusive *upper* owner revision on its first page; same `(generation,upper_revision)` on all pages and signed `(revision,change_ordinal)` cursor (ordinary one-subject edits have ordinal 0; any server-internal multi-item event must still carry unique ordinals), so continuously appended writes cannot starve completion. Checkpoint only `complete=true`; if cursor expires restart from original G/R, dedup by revision+ordinal, never skip a same-revision tombstone. Remove-all/withdraw increment generation and invalidate **all** earlier snapshot/export/change cursors and after_revision even for unseen subjects; return 409 `generation_conflict` or `snapshot_required`, never an empty authoritative page. Subject erasure advances non-identifying floor, removes its historical versions and invalidates affected cursors/deltas likewise. At 90-day delta retention expiry return `409 snapshot_required`; Android at **30 days offline** requires new device browser approval and full snapshot even if server still has deltas. Only create encrypted pending intent while unlocked/currently proved; never transmit credentials/counters/private profiles. Under invalidation discard partial pages, retain protected local state until fresh proof and explicit rebase. Rate-limit **every** route per owner/device + project with integer `Retry-After` 1..60; reject large POSTs before parse and return no 3xx on authenticated APIs.
