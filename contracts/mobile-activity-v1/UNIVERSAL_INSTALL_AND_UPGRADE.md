# Mobile backend install/upgrade — any compatible deployment, NO automatic GO

No Flare-specific override is required. **PostgreSQL must boot with `track_commit_timestamp=on` before approval transactions that may be measured.** PostgreSQL's `pg_xact_commit_timestamp(xmin)` only covers transactions committed after activation; VACUUM may discard older commit timestamps. Neither enabling the setting later nor migrating 069 reconstructs old approvals or expired ClickHouse source. Unprovable history is **Not recorded**, never an eligible zero/retroactive positive. When **mobile issuance is enabled**, init fails before an unsafe upgrade if the setting is off or a restart is pending (`MOBILE_PG_COMMIT_CLOCK_UNAVAILABLE`). For ordinary installations with mobile disabled (including GCP Cloud SQL), schema migrations may proceed with a warning; mobile evidence remains Not recorded and mobile must **not** be enabled. This is an operator stop for mobile, not a request for manual SQL surgery. Read-only status from the exact image: `/app/.venv/bin/python -m services.mobile_boot_preflight` (with its usual `DATABASE_URL`; never print the URL). It differentiates `OFFLINE`, `OLD_OR_INCOMPATIBLE_SCHEMA`, `MISSING_DB_PREREQUISITE`, `MOBILE_NOT_CONFIGURED`, `PRIVACY_CLOSED`, `EVIDENCE_UNQUALIFIED`, and `PREFLIGHT_ONLY`. Even `PREFLIGHT_ONLY` is not a person-specific read grant or installed-app pass. Public `/readyz` is not that proof.

Read-only preflight against **only an authorized instance**: confirm immutable image digest for init/all API replicas/worker, `SELECT version_num FROM alembic_version`, `SELECT setting,pending_restart FROM pg_settings WHERE name='track_commit_timestamp'`, old/new publication counts (redacted aggregates only), database size/free space/replication/lock waits, backup age and a disposable restore's matching head. Read back ClickHouse migration log and both TTL expressions: **30-day `raw_line` column**, **90-day whole-row**; check worker high-water, Redis persistence/availability and revocation denial. An application boot or migration PASS does not grant person reads. Keep `blocked=true` and no demo seeds until explicit privacy/evidence review, and never interpret a follow as consent to view activity.

**Disposable-only rehearsal, not an operator shortcut:** `tests/integration_mobile/test_mobile_upgrade_restore_postgres.py` requires `MOBILE_MIGRATION_SCRATCH=1`, an exact loopback PostgreSQL 18 scratch host/port/database assertion and a separate restored database. `MOBILE_MIGRATION_ROWS` defaults to 1,000 and is asserted between 1,000 and 100,000 fabricated pre-069 approvals; it reports elapsed 069 time and publication relation total bytes before/after. At 10K/100K on a disposable 2026 local host it observed 0.912/4.148 seconds and 2,318,336→3,547,136 / 18,030,592→34,955,264 bytes, respectively. The test drops its scratch databases; the disposable PostgreSQL container must also be stopped and removed by its launcher; it has no evidence of concurrent writers, realistic migration triggers, candidate lock waits, WAL/free-space margin or production performance. **Never** point its environment at a shared/candidate/dev/prod database. Logs: `/tmp/mobile071-ten-k-restored-upgrade.log`, `/tmp/mobile071-hundred-k-restored-upgrade.log`.

**Populated 069 upgrade:** inventory largest `mobile_publication_events`, fact volumes, WAL capacity/locks and readers under an isolated candidate-sized *restored* copy, then time the migration with `pg_stat_activity` and `pg_locks`. 069's table-wide update can trigger per-row epoch work, so set a bounded approved outage and recovery threshold; if exceeded, abort transaction, keep serving closed or restore from the tested snapshot. It refuses downgrade. Preserve ClickHouse and Redis retention/revocation separately in the backup runbook; restore-test application-side key and exact image/DB combinations. On resume, old approval commit times and expired source **stay unqualified**—there is no SQL patch to manufacture them. Fresh install still requires same-image init/API/worker and actual TTL/Redis/closed-barrier readback. No Flare inventory, image attestation, database restart or backup restore is claimed by this document.
