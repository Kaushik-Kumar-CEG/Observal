## Android v1 preference decision honored

Sync **only subject UUID bookmark identity**. Global `1w`/`1m`/`3m` period and visibility choices are **device-local**, exactly as Android requested; so are theme, selected API origin, browser choice, tokens, local intent queue, device ID and cached counts. No per-person period or phone-specific UX choice is stored, transmitted, or implicitly imported. A follow never grants Author/User scope; public identity resolution must use current v1.2 `/people/resolve`, omitting removed/non-public people without previously cached names or roles. A bookmark to an unavailable UUID can be shown only as a generic unavailable entry and can be removed by the owner without disclosing identity/activity.

Account-owned metadata partition key: immutable **server UUID + server-provided project ID (`default` on current installations) + viewer UUID + cohort**; server also binds the selected HTTPS API origin and approved mobile device at every request. No transfer or fallback between accounts/projects/servers or between synthetic and live. Store bare subject UUID, monotonically increasing per-subject revision, minimal owner revision and write outcome; **no** email/name, activity, role, component ID, trace, token or browser URL. Disclosure before opt-in: private bookmarks are stored on this server for this account across separately approved phones; following confers no activity access; phone unlink/logout does not erase account follows; remove all is a separate explicit account operation. Current valid device/Redis/account revocation and SCIM deactivation are checked on every route, including cursor/delta/status requests. Account/DSR erasure removes bookmark, high-water, tombstone, dedup, removal/consent records; **subject** erasure transactionally removes that UUID from **every owner's partition** and installs a non-reconstructive global subject-deletion fence serialized with follow writes. New follows must lock and prove the current public/live subject before commit; replays for deleted/nonpublic UUIDs return 403 without redisclosing names. Deletion fences outlive pending op/dedup windows and UUIDs are never reassigned. For each affected owner, erasure atomically advances a non-identifying owner **erasure-floor revision**, removes that UUID from point-in-time versions/change history too and invalidates older signed snapshot/export/change cursors; older `after_revision` returns 409 `snapshot_required` (never a partial redacted delta). A snapshot cursor made before this erasure returns 409 `stale_snapshot`, requiring fresh full owner snapshot. Floor is a number, not a persistent erased-subject reference. A failed global cleanup keeps follow reads/writes closed until repaired. Audit retention is independent and must not reconstruct subject follows. Per-partition owner-only paged export is `/export`. No silently added real-person access on upgrade.

## Negotiation and narrow write authority

A freshly proven accepted-v1.2 `mobile:read` grant calls `GET /mobile-follow-sync/v1/availability`. Version `1.0.1`, exact server/project/viewer/cohort, `state=disabled|consent_required|restricted|available`, page limit 100 and offline horizon 30 days are **separate strict JSON**; no v1.2 capability field, validator relaxation or response-meaning change. `consent_required` is different from disabled, offline or privacy restriction. Explicit `POST /consent` only records opt-in after Android disclosure; it does not create follows. A current `mobile:read` token alone has **no authority to mint a write grant**. Each phone first `POST /write-authorization` obtains an ≤600-second user code bound to this device/partition, then the human separately signs into the real same-server browser and explicitly approves the follow-write scope for **that one phone** using `POST /write-approval` with a normal desktop/browser account JWT (never a mobile JWT). The challenge does not redirect the mobile token to the browser; code possession alone cannot grant access. Its one-use binding is checked with the live account and closed barrier; unlink/logout/SCIM/revoke removes or invalidates per-device approval. `POST /write-grant` re-proves the current mobile read JWT/device, account, server/project/cohort, **that separate approved-device record**, consent, barrier and Redis, returning a **distinct unrefreshable ≤300-second** JWT with `aud=observal-mobile-follow-sync-v1`, `scope=mobile:follow-write`, same device/user/cohort and NO refresh credential. The existing `/auth/device/token`, `/auth/token/refresh` and `/auth/mobile/credential` continue to return and verify **exact existing v1.2 mobile:read**; they never mint a general API write credential. Only `/operations`, `/removals/prepare` and `/removals` accept the new follow-write token; reject it for v1.2 reads, admin/registry/legacy REST/GraphQL, cross-user, cross-project or cross-server. A 401/403/503 locks local cleartext, never clears encrypted same-account pending intent by guessing server state.

## Single-operation and two-phone semantics

`POST /operations` accepts **exactly ONE** conditional `{operation_id,subject_id,base_person_revision,action:follow|unfollow}` per request; no list upload, batch partial-commit ambiguity or arbitrary 250-follow cap. The server transaction locks the owner/subject row (or advisory-keyed partition for first insertion), validates max 4096-byte UTF-8 JSON and UUID forms, and commits a new global revision + per-person revision + op outcome atomically. If a new subject was never followed, its revision is **0**; after unfollow it is absent from active snapshot but **not** revision 0. A partition permits at most **100,000 distinct subject UUIDs across its lifetime** (including removed high-water rows), enforced transactionally with a bounded counter; at capacity, new subjects receive 409 `capacity_reached` and existing-subject unfollows and account remove-all remain usable. This is an explicit storage/backup/erasure bound, not a 250-active-follow ceiling; raising it requires reviewed quota/cost evidence. Same-person add versus remove: first valid commit wins; second receives **HTTP 409** `person_conflict` with current person/global revisions and must ask the user to **explicitly** rebase by retrieving fresh owner snapshot and issuing a **new** operation ID/base revision. The 409 conflict supplies authoritative `person_revision` **and `current_following`** for that same owner-submitted UUID, even if absent from active snapshot. After old change history expires, the new snapshot alone cannot provide the absent subject's high-water: ask for deliberate user intent before a conditional base-0 op; if it conflicts, use that conflict's revision/state only after renewed explicit user confirmation with a new op ID. Never silently retry a stale follow on unseen state. No automatic last-arrival-wins, no stale full-list overwrite. Independent subjects commute. Reusing an op ID with different body is 409 `operation_id_reused`. Duplicate `(server,project,viewer,cohort,operation_id)` with identical body returns the **same status and JSON**, including prior 409, for at least **90 days**. Commit-before-200 is mandatory; lost 200/409 is ambiguous, `GET /operations/{operation_id}` returns stored outcome when present, 404 means unknown **not** guaranteed uncommitted, and retry uses the **same** ID/body rather than inferring from a timeout; 410 after retention requires fresh snapshot and explicit intent rebase. `base_person_revision` includes a minimally retained high-water mark for a removed UUID **for the lifetime of the account** (no name or period); expiry of 90-day full tombstones/dedup must never reset that revision, resurrect an old follow, or invent unsupported zero.

`GET /snapshot` returns at most 100 UUID bookmarks per keyset page, **revision-pinned** owner/global revision, `next_cursor` and `complete`. Concurrent phone writes do **not** invalidate a live cursor; retain bounded point-in-time subject-version history at least until ≤15-minute cursor expiry, so the original snapshot makes progress independent of concurrent edits. Finish pages at that revision, then fetch `/changes`. Expired/forged/boundary-invalid **or affected-subject erasure-invalidated** cursors return 409 `stale_snapshot`, requiring a new full snapshot; never upload partial pages as a full replacement. `GET /changes?after_revision=N` freezes an inclusive **upper owner revision** at its FIRST page; every subsequent page returns that same upper `revision`, even while another phone commits. Its opaque signed `(upper_revision,revision,change_ordinal)` keyset cursor is bound to owner/server/project/cohort and erasure floor, expires ≤15 min and never omits same-revision tombstones after a 100-item page. This bounded traversal completes under continuous writes; start a new traversal from the completed upper revision to catch later writes. If erasure advances the floor mid-traversal, return 409 `snapshot_required`, discard partial pages and take a new full snapshot. If N precedes 90-day change history, 409 `snapshot_required`, requiring new proof, full snapshot and deliberate per-person rebase. **An incomplete change page is never a durable scalar-revision checkpoint:** persist ORIGINAL `after_revision` plus cursor until `complete=true`; after cursor loss/expiry restart from that original revision, deduplicate by `(revision,change_ordinal)` and only then advance checkpoint to the completed response revision. This protects a tombstone after a same-revision page boundary. Even if changes remain server-available after day 30, Android must take fresh approval and full snapshot instead of consuming the delta. Offline edit retention: Android only creates protected pending intent while an already proved session is unlocked; after **30 days** offline (at most the original refresh family), require fresh browser approval and full snapshot **before** considering any old intent, never blind replay. Legacy encrypted local-only follows import after first same-account login uses one conditional op/person and preserves the only ciphertext on error. No credentials, counters or private profile data are uploaded. Index `(server,project,viewer,cohort,subject_id)` and `(server,project,viewer,cohort,revision,change_ordinal)`, bound response length and rate-limit **every route** per current owner/device plus project budget (including code/grant issuance, export and status checks; integer `Retry-After` 1..60). Every POST rejects >4096 bytes **before parsing**, returning 413; check rate budgets before DB work without user-existence leaks. Require measured historical keyset-query plans, retention/compaction and backup/DSR cost at the declared 100,000-subject lifetime cap, not an undocumented 250-follow ceiling.

## Explicit remove-all, export and stop states

Unlink this phone = existing device logout, **not** account delete. Remove **all** account follows = explicit two-step `POST /removals/prepare` after current owner proof and fresh ≤5-minute write grant; server issues one-time ≤120-second nonce bound to server/project/viewer/cohort/device. Android must confirm account-wide removal, then POST `/removals` with `{nonce,confirm:true}`. **202 `pending` is not deletion success**. Durable owner fence denies follow edits and partial paged reads while background batches of ≤100 emit tombstones with unique `(revision,change_ordinal)` keys; interrupted jobs must resume idempotently from committed cursor. `GET /removals/{id}` returns `pending|needs_operator|completed` and durable revision; only `completed` permits new snapshot, never phone logout in lieu of removal. Worker retries bounded batches idempotently with durable offset and alerts on repeated failure, marking `needs_operator` without falsely reporting completion. A named authorized operator must audit, repair the cause, resume from committed cursor and reconcile all rows before advancing to `completed`; until then the partition remains closed. No automated reopen or rollback from partially erased state. A second identical POST with a consumed nonce on the same owner/device returns the **same original 202 body and removal ID** for ≥90 days without starting another job; a mismatched body/device/project is rejected 409. This makes a lost 202 idempotently recoverable; an unsubmitted nonce expires and has no effect. Cancel only before submission by letting nonce expire; after accepted 202 the operation cannot be rolled back without resurrecting deleted follows. `/export` pages current UUID bookmarks/owner revision, never names or activity. Consent disabling, account deletion and regulatory erasure require backend DSR integration; account deletion purges all partitions and revoke markers, never recreates a follow after cleanup.

Errors: 400 malformed, 401 wrong/expired/revoked audience, 403 wrong owner/cohort/consent, 404 absent extension or unknown op (distinguish by path and proven server version), 409 conditional conflict/stale snapshot/too old, 410 expired dedup, 413 >4096 bytes, 429 per-owner/device fair limit with integer `Retry-After` 1..60, 503 offline/closed barrier/Redis/removal pending. Strict `{error:string}` with no private subject details except owner-submitted subject revision on op conflict. No 3xx redirects on authenticated APIs. Browser verification origin may be distinct from the selected API HTTPS origin, but token is **never redirected there**; `/device` must load actual SPA JS and confirm code against the same issuing server, not a foreign backend. The new feature cannot open default-closed person reads on install or upgrade.
