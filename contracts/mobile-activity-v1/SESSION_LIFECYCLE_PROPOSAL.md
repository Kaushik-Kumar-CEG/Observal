# Joint Android/backend mobile session lifecycle — proposed, Android ACK required

**Status: PROPOSAL, not an accepted wire change or Android READY.** This document is the backend's request to the Android session in `/home/kaushik/projects/observal-mobile-production` for a decision *before* any changed API/wire behavior. Preserve accepted v1.2 `openapi.yaml`, `fixtures.json`, `responses.json` and `contract-vectors.json` byte-for-byte unless both owners approve a versioned change. The 068 backend and RC18 TEST APK are historical baselines, not final pins. No protected Flare cohort may open to validate this design.

## Invariants and outcomes

- **First approval / no saved grant:** use the explicit existing `observal-mobile` device challenge and one-use browser approval. Confirm an HTTPS-origin `/auth/mobile/credential` proof (exact client `observal-mobile`, device ID, audience `observal-mobile-activity-v1`, `mobile:read`, user) and `/mobile-activity/v1/capabilities` for that origin, server, project and viewer *before* saving a pair or revealing bookmarks/counts. No demo or CLI/browser token fallback.
- **Ordinary full app quit/reopen:** keep the encrypted same-origin/identity refresh grant; begin **locked**, with no stale count or bookmark exposure. With an unexpired access token, obtain fresh credential proof and capabilities; with an expired access token, perform **one** mobile-scoped rotation, then obtain fresh proof and capabilities. Only a matching origin/server/project/viewer/device and an authorized cohort silently resumes and decrypts same-account follows. An expiring access token while an app is open uses the same serialized path. This is persistent login, not a browser approval on every restart.
- **Capability changes:** supported kinds, `platform_overview` and other optional capability *availability* are not identities. Re-fetch capabilities, clear old in-memory readings/cursors and reauthorize each view; no previous count becomes supported zero. A different server ID, project ID, viewer ID, device ID, client/audience/scope, lost scope or revoked permission locks access. A different selected origin requires explicit source selection and fresh authorization, never cross-origin token forwarding or silent migration of follows.
- **Concurrent HTTP / rotation:** phone serializes one refresh per stored grant; server consumes an eligible predecessor and registers exactly one successor in **one atomic Redis operation**, rechecking account/device revocation there. Competing rotations are denied (401); neither can mint another successor. Bind the successor to the same user, device, mobile client, audience/read-only scope and immutable original refresh-family deadline; no unbounded sliding 30-day family. A valid successor is never returned when Redis fails or the operator's issuance gate is disabled. No phone use of refresh credentials for browser/CLI/GraphQL/general person endpoints.
- **Offline / 503:** stay locked and keep encrypted grant and same-account follows inaccessible. **Retry** is for fresh access credential/capability probes, failed native reads, or a refresh *proven never dispatched*. Before handing a refresh to HTTP, Android durably fences the predecessor; a network-dispatched timeout/503 is **ambiguous**, not retryable with that predecessor. Offer exceptional browser approval directly. Never infer from a timeout or 503 that Redis did not commit rotation.
- **Lost refresh reply / process crash:** if process death occurs before HTTP dispatch, a proven unsent predecessor may be used after restart. From dispatch until the *successor is durably saved and proved*, the predecessor is ambiguous and cannot be retried, even if a reply was never seen. **No recovery/replay endpoint in v1.2**: no way to authenticate a lost successor from that predecessor without permitting stolen replay or two successors. Stay locked and offer an **exceptional fresh device/browser approval immediately**, without waiting for a 401; preserve encrypted follows only when the newly proved origin/server/project/viewer matches and no explicit logout/switch tombstone exists. After durable successor save, a restart uses the new pair normally. This exceptional approval is not approval on every ordinary restart. No arbitrary replay, guessed local identity, sliding token family or signed-out fake account.
- **Expired or revoked refresh, account deletion/deactivation, device revocation, audited operator cohort disable/revoke:** deny refresh and every protected read for a terminal revocation. Reversible operator pause locks reads and issuance; after separately authorized re-enable, an old unexpired *non-revoked* family can qualify only after fresh proof/capabilities. A terminally revoked device/account/family remains denied **even after re-enable** and even before an access JWT expires; Redis failure always fails closed. An offline sign-out **locks locally and durably fences immediately**, then attempts existing `/auth/mobile/logout` best-effort with its last pair. If access has expired or remote revoke fails, report **remote revocation unconfirmed**; do not rotate during logout, delay local lockout or claim success. A revoked family is not recoverable using its old saved grant. A live↔synthetic cohort change is not an optional capability drift: lock and require new explicit authorization; within one cohort, kinds and optional overview can change after fresh permission checks.
- **Verification, response and display:** received refresh metadata is not trusted until `/auth/mobile/credential` and capabilities pass. Do not widen Authorization to other APIs. Keep scoped Author/User distinct-root facts, MCP/Skill/Hook evidence, Restricted/Not recorded, retention and approved publication unchanged. After any refresh or capability change, discard stale in-memory counts until refetched; an unsupported kind never becomes a supported zero. The accepted Android validator remains strict.

## Wire decision requested from Android

**Preferred: no v1.2 wire changes.** Keep `POST /auth/token/refresh` (`{refresh_token}`), its exact mobile response, and existing credential/capability probes. New server guarantees affect Redis rotation ordering and JWT family lifetime only. Android needs a locked cold-start encrypted-grant recovery path and must avoid deleting follows on ambiguous refresh; implementing this accepted lifecycle on the *unchanged* v1.2 HTTP wire is an Android source change, not a wire version bump. Any additional endpoint, response field, altered HTTP error/status or widened scope requires a separately reviewed versioned contract and explicit Android approval. **Awaiting Android owner/session acknowledgement** of ordinary-restart, ambiguous-rotation and exceptional fresh approval outcomes. A unilateral backend proposal is not agreement.
