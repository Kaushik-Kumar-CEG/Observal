## Four fixes for draft discussion (subject to Android/owner review)

1. **Bounded leases at first request, including 429:** Propose **1,000 distinct subjects per owner/project/cohort/generation** (not 100,000) for named product-owner decision. Fixed 100-item pages: at most 10 pages/lease. One shared owner-wide snapshot/export image + one fixed-upper change lease; ≤2,000 pinned UUID/event rows and a **1 MiB logical pinned-data reservation** per owner/project/cohort, enforced transactionally with the first request; no private names or counters. No new query ID or per-device admission table: the first cursorless request is serialized on its canonical owner/project/cohort/generation/erasure-floor **purpose + (for changes) starting revision** key. The server reuses the current owner-wide image/change lease for an equivalent request; a different device may join the same image without allocating another. A lost cursorless first 429 repeats the same URL and receives the **same lease** (and no second 429 for that page); first-429 retry_cursor additionally names that same lease. A competing non-equivalent change window cannot displace the active lease and falls back to shared snapshot. First 429 carries the same `retry_cursor` and lease ID. Different change R while its one slot is occupied fails closed with recoverable `409 snapshot_required` so the client may use/reuse the shared full snapshot. A genuinely full storage reservation returns `503 unavailable` **before a page or first 429**, never an indefinite queue or eviction of a valid in-flight reader. Revised after independent draft review: leases expire at a fixed **15 minutes** (10 pages × worst 65 seconds = 650 seconds <900), then cleanup releases rows/reservations. The extension's `availability.current_revision` tells a reader its fresh target; a snapshot request with `min_revision` MUST NOT reuse an older pinned image and returns bounded `503 unavailable` with `Retry-After<=60` until that image expires (≤15 minutes), then admits a new current image. This is **bounded delayed freshness, not immediate second-phone sync**; Android must not label stale pinned state Synced. Completion time is NOT pin time. Different R on the one change slot also falls back through fresh `min_revision` snapshot, not a loop on a stale image. No unbounded admission-ID or cursor-replay table may grow from cursorless requests. Subject erasure/withdrawal immediately purges/invalidates pinned material. No claim that PostgreSQL physical index/WAL/backup overhead fits 1 MiB: it must be separately measured and owner-approved before enablement. Project-wide capacity admission is fail-closed; qualified arbitrary user count is NOT claimed for a finite store.
2. **Lost 200 means HISTORICAL, never current Following:** The status lookup proves a prior operation committed, NOT current state. `effective:true` only means generation/consent/erasure fence valid at lookup time. Android retains pending/review status until a subsequently completed, verified snapshot or fixed-upper change checkpoint at revision **≥ the applied revision** explicitly confirms X's *current* following/person revision. If phone B unfollowed after A's lost 200, A must show Not Following or conflict after that checkpoint, never Synced, never auto-replay. If more concurrent writes occur after the checkpoint, the displayed following is only as-of the committed checkpoint. Retain the exact HTTP/outcome type coupling from 1.0.3.
3. **Redacted 409 shape:** `person_conflict` has the only per-person `revision`, `person_revision`, `current_following`; **every** other 409 error variant (`generation_conflict`, `subject_erased`, `capacity_reached`, `operation_id_reused`, `revision_exhausted`) has only error, operation ID and owner generation. Strict OpenAPI `oneOf` with `additionalProperties:false` on **each branch** denies private extra fields/nulls, including erasure and owner reset. Android rejects unexpectedly present per-person fields even if null.
4. **YAML parsing repair:** Quote/multiline-encode every affected flow-map `description`; recursive test rejects **every** null mapping value or unexpected key in all 17 paths/components/responses (1.0.3 parses 19 null keys across 18 descriptions). Round-trip OpenAPI generation must preserve all meaningful text; plain YAML load succeeding is not enough.
