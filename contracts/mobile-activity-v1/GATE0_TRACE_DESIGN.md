## Immutable product arithmetic

The maintainer's 1W Following card has two distinct qualified *component-attributable logical-root runs* per person: Author (provably originally authored visible approved-at-event components, across eligible users) and User (subject's own authorized component use). Across the same paired half-open `[start,end)` UTC 7/30/90-day window, 40 MCP calls on one root = **one** trace; two components on that root give two component rows of one and **one** person union. Distinct actor-run keys are counted **after** listing visibility and scope filtering, never added across rows or followed people. Calls/confirmed loads/recorded runs are secondary typed facts. A verified **unprompted** root with attributable component activity counts in component traces; general prompted roots require a valid user prompt at/before qualifying in-window activity and are separate. Platform active accounts and prompted sessions are a separate privileged completed-day cohort, suppressed together below ten or on unsafe coverage.

## R1 — prospective run identity, NOT a historical guarantee

**Observed:** `002_session_record_identity.sql` stores `(project_id,user_id,harness,session_id,line_offset)` and nullable `parent_session_id`, **no run-incarnation**. Current Pi extension `observal.ts:303,909,953` uses `ctx.sessionManager.getSessionId()` as session ID and keys cursor/outbox on it; its payload omits `parent_session_id`. The delegated CLI generates a fresh `uuid4` and starts Pi with `--session-id` (`delegation/local.py:210-230`, `harness/pi.py:183-198`), but the separate task ID/agent attribution is not a server-verified **parent run link**. Current mobile projection may classify a delegated child as an independent root. Pi's CLI reconcile adapter inherits an empty source-discovery method; extension startup recovery is separate and bounded. Other supported harness IDs/restart/fork guarantees have **not** been proven; `AGENTS.md` capability support does not prove runtime attribution.

**Selected prospective design to prototype:** sender persists a random per-run incarnation UUID (or equivalent immutable server-issued nonce), created only at a verified new run, retained across reconnect/resume/retry/source repair, bound at ingest to authenticated `(project,uploader,harness,sender_version)` and a durable source-start identity. Child uploader must send an explicit parent *incarnation* reference and verifiable delegation association; backend independently checks same project/uploader/harness, parent creation no later than child/activity, bounded acyclic chain, no ambiguous fork and a valid source revision. **Absence of a parent link is never proof of root origin:** only a server-verified launcher/root-start attestation bound to the incarnation (or harness-specific independently proven origin) may mark a run root; dropped link, self-declared root, untrusted launcher or unknown source makes reach unknown. A client-declared bare parent/session string alone is insufficient. The current CH events/checkpoints and PG fact keys need prospective migration or quarantine for same-user duplicate IDs; until migration actually identifies separate incarnations, **reject/quarantine same-scoped ID reuse, never merge or overwrite**. If the harness has a demonstrably immutable globally unique ID across restart/fork/import, the owner may adopt that instead **after** equivalence tests; do not add a parallel nonce merely by assumption. Legacy Pi source without verified parent/incarnation: root reach null when ambiguous/possibly delegated, or qualified **Partial observed** only for a separately demonstrated unambiguous cohort. Unknown calls can remain typed evidence without becoming a numbered root. No historical overwritten session can be reconstructed from a current digest, line offset or time heuristic.

**R1 fixtures:** same uploader reuses an ID for two runs (no collapse or fictitious distinct counts); two uploaders reuse same ID (separate); repair/resume one UUID (one); delegated child with no sender parent link (unknown rather than independent); two verified linked children of one root (one); cross-user/harness parent, cycle, future parent and root prompt after child (unknown); unprompted root with verified provenance (component one, general zero). Prove harness behavior under restart, resume, fork/import and recovery before adding it to advertised kinds. No real sender was upgraded in this branch.

## R2 — fail-closed control before async storage deletion

**Observed:** `services/retention.py` issues CH lightweight `DELETE ... SETTINGS lightweight_deletes_sync=0` for timestamp/count retention; PG evidence is not atomically deleted with CH. Draft `run_mobile_retention_sweep` checks ≤50 old publications each five minutes and a poison first entry can block progress; >14,400/day arrivals can outpace it. Successful rechecks change `updated_at`; this sweep is not a read fence. Current `mobile_activity_query.py` rescans source on every request but cannot scale to 10K+ roots. TTL might delete source independently. Account/SCIM deletion policy and backup erasure are not established by a mobile migration.

**Selected design for backend prototype, NOT a claimed cross-store transaction:** a PG **read-control generation and deny/pending-erasure barrier** checked with authorization in the same PG transaction on every summary/page/detail; readers take a transaction-scoped shared lock on the affected scope and hold it through query completion, while the erasure writer takes the exclusive lock, advances the generation and commits the barrier *before* starting CH delete. Requests starting after barrier commit cannot read old facts; a request that linearized earlier can finish after commit (including bytes already in flight). A stricter no-late-delivery guarantee needs an explicit network response/erasure protocol and is **not** claimed. Atomically revoke PG-derived facts/caches or make them unreadable. Keep a durable minimal replay-rejection epoch per erased uploader/scope, with sender reissuance rules: reject pre-epoch run incarnations, revoked credentials, delayed outbox and source repair even after physical deletion; do not retire the marker solely because CH delete completed. Retention/lifetime and account deletion of this marker require privacy-owner approval; if no lawful durable replay fence exists, forever reject the affected legacy upload identity. Reject any replay while the barrier is active. **Ingest and projection writers must hold the same scope lock through their epoch comparison and fact commit**, and recheck source revision at commit; erasure waits for them or they see the new epoch and abort. An upload that passed an earlier check cannot publish facts after erasure commits. If the barrier write fails, do **not** initiate an unsafeguarded deletion and do not return a complete reading for affected scope. CH delete happens asynchronously, checked with mutation/TTL completion and retries. Source-derived PG facts are deleted on a monitored, fair expiry/revocation queue with quarantine/backoff of poison entries and an **owner-approved deletion deadline** (not yet selected). Deactivated/deleted accounts must not appear in named cards; explicit privacy erasure cannot rely on the source TTL alone.

For scheduled time/count retention, publish a conservative pending-purge/coverage-floor control **before** issuing delete; intersecting windows cannot remain `supported` once an unverified source or suffix is possible, even before CH mutation completes. Autonomous CH TTL has no guaranteed synchronous notice: either select a bounded safety horizon from effective CH schema + measured projection/source lag, with fail-closed reads when lag/floor is unknown, or disable complete numeric reads for affected windows. An in-window retained suffix can contribute only if its event and root lineage independently qualify, marked Partial; fully lost source is unknown, never zero. Replay/source repair creates a new qualified generation idempotently; card→detail and page→page check viewer/scope/visibility and generation, returning `stale_cursor`/unavailable on mismatch. A pinned end is not an immutable database snapshot. Unrelated writes must not invalidate all pages: use a scoped generation or short-lived snapshot lease with a bounded restart/forward-progress policy. **No synchronous PG+CH atomicity is asserted.**

**R2 fixtures:** upload/projection begins before erasure but attempts fact commit after its barrier (must abort or serialize before erasure), explicit erasure committed between card and detail or pages (old complete count cannot be served); CH delete fails after barrier (still denied and retried); delayed TTL/count purge before slow sweep (Partial/null), straddling/full purge, erased-user replay, poison first cleanup item followed by expired second, 50 permanently pending projection items before qualified item, >14,400 daily expiries with bounded deletion deadline, and hundreds of component pages during unrelated writes without starvation. Actual PG/CH races, delete deadline and backups remain Gate 1/policy approval, not proven here.

## B-scale — indexed PostgreSQL event facts plus separate eligibility ledger (provisional choice)

**Observed:** draft MCP query revalidates ≤20 positive candidate sessions/40,000 source lines per read, component result ≤20, batch ≤5 subjects; general roots ≤20/person and ≤100/platform. It cannot prove eligible zero or support the illustrative 10K/4K volume. Its source validator uses separate `user_id IN ...` and `session_id IN ...` filters, which materialize irrelevant Cartesian cross-pairs. Its Pi extractor can fall back to inherited/ingest CH timestamps for undated source calls; forbid that for period attribution. Backfill currently limits source scans to 90 days even where retention is longer. These are **not** reasons to raise caps.

**Selected candidate:** a PG partitioned/indexed *qualified event fact* keyed by `(project, actor, harness, verified_run_incarnation, source_generation, event_key, listing_version)` and original **source** UTC event time; unique idempotent event keys and current generation membership. Index `(project,actor,event_time,root)` and `(project,listing,event_time,actor,root)` with tested include columns. Do not compress away event times into UTC days: rolling 7/30/90-day starts can fall mid-day. For each viewer request join event-time approval/original-author provenance and **current** authorized listing visibility before counting `DISTINCT (actor,run_incarnation)` for person Author or User; group by listing for row reach independently. A root with two kinds/versions/components is one union. A separate bounded indexed *eligible zero-positive session ledger* records verified mapping/instrumentation/source window/sender version/projection status even if no event fact exists; unknown cohorts and retention coverage prevent false supported zero. Pub/visible facts cannot be permanently baked into cross-user author totals. General prompted root cohort is independently projected and gated. A joined read should not materialize raw JSONL on each card; verification/revocation work moves to bounded fair jobs and read-control barrier/watermarks. Alternative CH materialized fact+PG ACL is possible only if it passes the same cross-store revocation tests with no privacy leakage; decision favors PG facts to keep listing/permission joins and explicit barrier together.

**Provisional API limits, NOT observed backend p95:** 12 visible people/two scope readings per viewport; if a five-subject batch remains, at most two in-flight capped requests and three requests/viewport; 20 rows/page; response ≤64 KiB; warm server p95 target ≤500ms viewport, ≤300ms summary, ≤500ms page/detail at ≥100 follows, ≥10K qualified roots per person, 90 days and overlapping components. Measure cold paths/queries separately and revise budgets with evidence if needed. Cursor binds viewer, subject/scope, paired server window, authorized visibility and scoped evidence generation plus ordering position; a short-lived lease must permit hundreds of rows despite unrelated writes or explicitly bounded restarts. Summary union is over whole eligible dataset, never page sum. No production-like PG/CH `EXPLAIN` or live p95 was run. A **disposable SQLite in-memory demonstration** (`python3 contracts/mobile-activity-v1/prototype_sqlite.py`) seeded 107,101 event facts and 59,500 eligible roots (one actor 10K, 100 actors), verified 9,000 observed roots versus two 9,000-row overlapping components, a zero-positive 1,000-root cohort and author visibility recheck; measured SQLite-only 12-actor/two-scope p95 **8.9 ms, 17.1 ms and 20.3 ms** in three 30-trial runs of the tracked script on this machine (an earlier equivalent disposable /tmp run measured 13.9 ms; none is a target). SQLite query plans used actor/day and component/day indexes and temporary distinct B-tree; this proves neither PG partition viability nor HTTP p95, stable paging, source coverage or retention safety. Re-run real PG/CH with synthetic workload at Gate 1.

## Wire, access and mobile agreement

Because the old v1 is an **undeployed** negotiation draft, correct that **one** backend-owned `mobile-activity-v1` contract with an explicitly qualified `trace_headlines` capability; introduce v2 only if real deployed clients require backwards compatibility. Capability defaults **false** and remains false through this design branch. Person summary supplies **two separately authorized distinct-root readings** with paired server-issued fixed `[start,end)` UTC 1w/1m/3m bounds, `as_of`, opaque scoped revision/window token and evidence cohort; breakdown/detail inherit that exact window and reauthorize every read. A period change mints a fresh paired anchor. A forbidden scope returns 403 with no count/denominator/harness/source/hidden-listing clue. Ordinary user gets own User; cross-person scopes require trace-authorized admin under `security.trace_privacy`; own Author across others is **Restricted** pending separately approved aggregate disclosure. Following is a bookmark only. Author counts public, originally submitted, provably approved-at-event and currently visible listings across users; pending/private *self* User evidence is independently authorized, not subject to author approval, but the current projection rejects it. Authenticated read-only audience/scope mobile credentials and device-only logout are mandatory for real sign-in; existing `feat/mobile-scoped-auth` is unmerged and needs central REST/GraphQL/WebSocket denial proof.

Reading statuses: `supported 0` only for fully eligible declared cohort/window; `partial N` including partial zero only for verified subset and rendered/spoken **“N observed traces · Partial coverage”**; `not_recorded null` on unknown-only or absent source; Restricted/403 redacts everything. Separate typed MCP call/skill load/hook run counts are never headline unions; no supported union if a relevant kind/harness is missing, even if a typed MCP subset is valid. A 40-call one-run, two-component trace must return **1 person union and two rows of 1**. Status-specific wire responses forbid non-null `restricted`: denied scopes use a bodyless 403 only, without coverage or reasons; Author/User summaries are not interchanged. General prompted sessions and platform active-account/prompted-root counts are independent; platform completed-day reading jointly suppresses both below ten active accounts or insufficient source with identical neutral redacted nulls, no arbitrary filters, and suppresses cohort-sized timing work. Paged public directory returns no emails/roles; Published is approved visible original submissions, no activity permission implied. Session/raw transcript IDs never leave the aggregate API. Cold-start bookmark ID resolution needs a bounded identity-only read which omits deleted/hidden users; it must not reveal activity, previous names, or roles. A paired window anchor pins time and caller/project/period, while **each subject/scope** gets its own evidence/visibility revision used as a **required expected-revision precondition** for the first page and direct detail, as well as subsequent pages; mismatch returns 409 before count. Unrelated subjects' writes do not invalidate a cursor. Subject repair/erasure invalidates that subject's cursor even across batched pages. Current role and listing visibility are rechecked with per-viewer authorization and per-listing visibility epochs under the same shared/exclusive serialization rule as erasure: a change committed before a new read starts must not be served from stale cache. In-flight reads linearized before a role/visibility change may finish afterward; no recall of already-sent bytes is claimed. Multi-listing lock fanout and privacy-safe latency are Gate 1 proof obligations.

**Wire drafting status:** the schema and fixture examples on this branch are **negotiation-only**. The synthetic paired 40-call example is a **partial** union of one observed MCP root because skill/hook kinds are not qualified; MCP-only component rows can be supported independently. The separate supported-zero acceptance case requires all relevant kinds and an eligibility ledger. No backend route, sender incarnation, index, erasure barrier, zero-positive ledger, root linkage, mobile login, latency result or qualified deployed cohort is added here. Both backend and mobile owner must approve names/status rules/window/cursor/privacy before pinning these new bytes in the mobile repo. Existing September 2026 fixtures are synthetic and not current 1W. Never advertise `trace_headlines: true` until S/1/1a and a compatible running instance qualify the actual cohort.
