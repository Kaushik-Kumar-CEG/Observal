# Mobile 12-subject performance gate — **500 ms not qualified**

**2026-10-16 final-code synthetic measurement:** Under Alembic 061 and final API/worker image `sha256:0ce6051f0933ee7eccae996e111598aaec2170e49c3e26d5bc6ae9a928e43259`, a rollback-only 100-follow/10K-root run measured Author union **328 ms**, self-User union **149 ms**, representative 12-subject first paired batch **202.1 ms**, same-viewport warm p95 **225.9 ms** (12 repeats), 27-batch p95 **227.2 ms** and privacy-filtered representative p95 **123.1 ms**. The earlier intermediate source-guard implementation exceeded PostgreSQL's **15-second** statement timeout on the paired batch even though individual unions took 421/215 ms; a no-lineage-guard control still timed out. An unconditional root-publication join was redundant and removed while preserving root and intermediate source checks in the bounded child-only guard. The subsequent repeat passed real-PostgreSQL expiry regressions and 10K arithmetic. Because the no-lineage control also timed out under earlier variable host load, the isolated timeout cannot be attributed uniquely to that join. The tests ran on one isolated, variably loaded host with a 12-sample warm p95 estimator, not target hardware or production mix. **Do not promote this one run into a guaranteed 500 ms SLO or silently change the product budget.** Capture Android's actual first-viewport interval separately; current list awaits the backend batch before rendering visible cards.

**22:00 UTC independent fresh-061 repeat (current code, separate loopback PostgreSQL 18):** Three rollback-only 100-follow/10K-root runs measured first paired viewport **1100.1 / 706.4 / 434.2 ms**, representative warm paired p95 **763.5 / 771.5 / 362.7 ms** (12 repetitions per run), and 12-subject mixed-page p95 **545.0 / 530.1 / 398.7 ms**. A fourth isolated `EXPLAIN` run measured author union **557 ms**, own union **209 ms**, first batch **436.4 ms** and warm p95 **346.1 ms**. The benchmark database and credentials were destroyed at **22:12 UTC**, before Android timing. Variability is large: two of three independent repeats miss 500 ms, and the first cold viewport exceeded **1 second**; these runs **fail qualification of the proposed 500 ms gate**, despite the earlier fast run. This is not Android device telemetry or a new SLO; no unreviewed 1-second budget is asserted. Exact rebuilt API/worker image for the new Android cohort is `sha256:a20e11c17beb8fd7d5737169b8eee2a6b3ebfc7b695b607713de96f34eefd38e` (the final audit capture-time guard is not on a live request path). A product owner must accept a measured device loading strategy or fund privacy-preserving query work before rollout.

`MOBILE_INTEGRATION_SCALE=1 MOBILE_TRACE_EXPLAIN=1` on a disposable loopback PostgreSQL 18 stack inserts 100 follows and 10,000 root facts inside a rollback-only transaction. It asserts one root for 40 calls, overlapping component rows, original-author transfer, visibility and scope invalidation. It does **not** represent production hardware or live source ingestion. The v3 HTTPS proof has far fewer roots and cannot qualify this budget.

`EXPLAIN (ANALYZE, BUFFERS)` of the author predicate showed a 10K-row `mobile_run_instances` scan (~34 ms in one sample), a ~12K-row visibility/run hash-join chain and a distinct-root sort (one sample ~552 ms). A proposed stringified UUID pair key was tested and **reverted** after a 1216 ms mixed-viewport p95; it would not safely reduce the distinct-root workload. A binary actor/root key and scalar user-root variant was also reverted after a co-loaded host did not complete the representative probe within 180 seconds; high memory/swap pressure makes that comparison **inconclusive**, not a regression claim. Removing the transaction-local hash preference produced >1 s representative reads and was also reverted. Cold and warm latency vary materially under concurrent ClickHouse/API/worker container load; neither this nor an isolated p95 justifies silently increasing the 500 ms target.

**Current candidate caveat (migration 061):** the 22:00 fresh-061 repeat above exercises the root/child publication checks but remains a rollback-only local timing, not installed-Android first-viewport or production-like p95. The superseded `sha256:2be5af37bba19d0e763c8101aa18ab1706e90ef3db8aec933aed4227c6b19758` was never a performance pass. Do not infer a product SLO from a fast isolated repeat.

**Actual visible impact:** the current debug Android list resolves each twelve-person directory batch and **awaits the paired trace response before it sets the visible people/cards** (`src/screens/LiveActivityScreen.tsx`, `loadPeople`). A 0.56–1.14 s backend p95 on these disposable, variably loaded machines therefore delays first-viewport card population by at least that duration, *plus* directory, TLS/network and render time. There is no per-person skeleton that would conceal this latency. **Product decision required before a qualified rollout:** either retain 500 ms as a hard gate and commission a dedicated query/denormalization optimization with source, privacy-epoch, approval-time and deletion invariants, or explicitly accept an alternative UX/SLO (for example, add 12-card skeletons while background work completes and set a separately reviewed p95 on target hardware). Do not cache named counts without epoch/source/retention invalidation. Do not turn slow/unknown into zero or show general-session totals as a substitute. Measure production-like hardware and approval/privacy mixes **only after owner authorization**; the current backend does not pass the proposed budget.
