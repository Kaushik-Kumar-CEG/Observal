## Bounded reads, retention and progress

`GET /snapshot` and `/export` use a fixed `limit=100`; every **incomplete** page MUST contain exactly 100 rows, and only the final `complete:true` page may contain 0..100. Lookahead detects when a full 100-item page is already final; no trailing empty 1,001st page. Any smaller incomplete page is **strict-schema invalid** and Android rejects it rather than promoting a checkpoint. `limit=1` and any value other than 100 fail 400. Results are pinned to one generation and global revision. **Not a 15-minute sliding cursor:** the serialized first request reuses (or creates once) one of the owner/project/cohort's TWO shared snapshot/export images or TWO fixed-upper change leases at `(generation,revision,erasure_floor)`; a signed opaque ≤1,300-character keyset token carries that durable lease ID, purpose and last subject key. `/changes?owner_generation=G&after_revision=R` durably leases a *fixed inclusive upper* revision `U` on first page and pins a keyset `(revision,change_ordinal)` through `U`; pages appended after `U` never enter this stream. At first admission the server counts eligible delta rows with an indexed, bounded `LIMIT 1001` query: if more than 1,000, reply `409 snapshot_required` **before serving any page**; a fresh full snapshot is the safe fallback. Thus any admitted stream has ≤10 data pages, as does a full 1,000-bookmark snapshot/export; ordinary single-subject edits have ordinal 0 and any internal batch must assign unique ordinals. No unseen event is skipped at a page boundary.

**Durable progress and liveness contract (all numbers enforced on the server, not a claimed timing from vectors):** every `/snapshot`, `/export` or `/changes` request uses **`limit=100` only** (omitted means 100; any other value is 400); ≤1,000 rows therefore need ≤10 pages, never 1,000 one-row pages. A lease and its pinned rows/versions survive API/worker restart in durable PostgreSQL and are readable for a **fixed 15 minutes from admission** (not renewed by a 429 or page; no 15-minute cursor-token expiry). A phone offline for ≥30 days must re-prove and take a new snapshot, never promote a partial lease. A change lease is admitted only when the **oldest required delta is at most 89 days old at admission** and the 1,000-row indexed limit holds; an older delta or retention floor returns `409 snapshot_required` **before any first page**. Fixed 15-minute lease plus ≤89-day-old required deltas never retains any row past the 90-day raw delta maximum. A snapshot/export lease pins a compact materialized owner-authorized current UUID/revision image for at most 15 minutes, not old raw source indefinitely; subject/account erasure purges that image immediately. The server validates fixed lease expiry, bound owner/server/project/cohort/generation/purpose and signed keyset on every request; a signed token alone cannot grant read. The initial page request reserves the lease and required retention **before returning even a first 429** (else 503, no first page). Every paging 429 (including the very first request without a cursor) returns a strict `{error:"rate_limited", read_lease_id, retry_cursor}` plus `Retry-After`; `retry_cursor` is a signed owner/purpose/lease/keyset token, bound to the **already pinned first-page generation/revision/upper** and valid only with current mobile-read auth. Android persists it encrypted without treating it as a page, retries the SAME endpoint (and original G/R on `/changes`) with `cursor=retry_cursor`, and rejects lease-ID/token or origin mismatches. Later-page 429 returns that same prior-page cursor. Cursorless requests serialize on canonical owner/project/cohort/generation/erasure-floor/purpose (and original R for changes); lost-first-429 retries and a second phone reuse the active lease and its page-0 fair-use state even if the retry cursor was lost. Snapshot and export may share each of TWO owner image slots when pinned at the same revision/floor, issuing purpose-bound cursors; a second phone may atomically reserve a newer image without evicting the first. Two different approved devices with distinct R receive separate fixed-upper change leases; each phone can hold at most one change lease, and equivalent cursorless requests reuse its own existing lease across first-429 loss/restart. A third different R receives `409 snapshot_required`, then attempts a fresh snapshot in one of two image slots (if both full, bounded 503 until ≤15-minute expiry). No change or snapshot cursor transfers read authority across devices; every call independently checks owner/device/Redis/barrier. No per-request admission mapping grows from repeated first requests. A qualifying authorized **admitted** lease has at most **one 429** (`Retry-After` integer ≤60 seconds) per next page keyset, durably tracked across replicas/restarts. After that retry, the next authorized request for the same keyset must produce a valid page within a configured ≤5-second processing budget or fail closed with `503 unavailable` when dependencies are unhealthy; it may NOT return another 429 for that page. Every first-page admission is subject to this bound. A lease may have at most 10 pages * (60s + 5s) = 650s (<11min), below the fixed 15-minute lease, provided the client makes the retry/request; unbounded offline time or continuous dependency failure cannot be promised. Ordinary concurrent writes cannot dislodge the pinned data; subject erasure, account removal, withdrawal, revocation or generation change overrides any lease **immediately** with a non-authoritative 409/401/503, purging subject-bearing versions and forcing a fresh authorized snapshot. A lease never prolongs erased data or the 90-day privacy maximum. Per owner/project/cohort at most TWO snapshot/export images plus TWO fixed-upper change leases, each ≤1,000 pinned rows: ≤4,000 rows and a transactionally enforced **2 MiB logical pinned-data** reservation including bounded row encodings and lease metadata. One approved device cannot occupy both slots of a single purpose while a different approved device waits. Project/global reservation and physical index/WAL/backup amplification need measured values and owner signoff; absent resource capacity return 503 before the first page or first 429, never an unsound cursor. Cleanup on fixed 15-minute expiry releases rows/reservations (completion does NOT evict another phone's shared lease); no valid in-flight reader is evicted or queued indefinitely. Physical PostgreSQL index/WAL/backup overhead must be measured separately and owner-approved, not disguised as this logical cap. Equivalent new readers reuse an existing owner-wide image even if both change slots are occupied; an unsatisfiable project-wide reservation fails 503 before a first page, never endless 429. For fresh proof Android reads extension availability's `current_revision` and asks snapshot/export for `min_revision` at least that value. If existing images are below the requested minimum, admit a fresh current image in an available second slot. Only when both image slots are occupied return `503 unavailable` + `Retry-After<=60` until fixed ≤15-minute expiry; NEVER serve an older image as current or evict an in-flight reader. At fixed ≤15-minute expiry GC frees rows; a fresh image pins current revision and waiting phone can resume. After 24 hours offline an unfinished partial lease has expired: discard staged rows and start a fresh authorized full snapshot, with no implicit consent/grant. At ≥30 days offline require fresh same-issuer v1.2 owner credential/capabilities proof and a new browser-approved write authority before sending old encrypted intent; under arbitrary continued writes each completed snapshot remains authoritative only at its own pinned U. This bounded stale wait may be up to 15 minutes and needs Android draft UX approval; a snapshot pinned at revision1 but completed after another phone's revision2 unfollow cannot validate the lost-200 follow at revision1. Android requires a later complete checkpoint at revision≥the known revision2; no automatic Synced based on wall time. The server cannot accept a lease if it cannot reserve the required materialized snapshot/version/delta retention and fair page admission; it returns `503 unavailable` **before any first page** rather than advertise support it cannot deliver. Healthy-store admitted pages must use indexed keyset access inside the 5s budget; overrun is a 503, never another 429. No owner-visible 1,000-bookmark qualification is claimed until real-store saturation, retry and storage/DSR tests prove these limits and a named owner approves the cost.

**Crash/partial-page rule:** Android stores the original G/R (for changes), fixed U and lease token + last durable keyset **atomically with encrypted staging**; only a fully parsed `complete:true` page for the same lease/purpose/gen/revision/erasure floor atomically promotes the staged set and its checkpoint. An incomplete page is not an authoritative list: no partial page, 429, timeout, crash, 503 or unvalidated cursor is authoritative, or advances the original R. Resume after restart with the last durable token; if the final response was lost, re-request the same cursor and deduplicate keyed items before promotion. A complete full snapshot is authoritative **at pinned U**, not at its later completion wall time and not a claim that later concurrent writes never happened; start the next fixed-upper change request at U. If the fixed lease expires or is invalidated, discard staged rows and obtain a fresh full snapshot (never promote the partial data); late 409 `snapshot_required` is not an empty list. Remove-all/withdraw increment generation and invalidate **all** earlier snapshot/export/change cursors and after_revision even for unseen subjects; return 409 `generation_conflict` or `snapshot_required`, never an empty authoritative page. Subject erasure advances non-identifying floor, removes its historical versions and invalidates affected cursors/deltas likewise. At 90-day delta retention expiry return `409 snapshot_required`; Android at **30 days offline** requires new device browser approval and full snapshot even if server still has deltas. Only create encrypted pending intent while unlocked/currently proved; never transmit credentials/counters/private profiles. Under invalidation discard partial pages, retain protected local state until fresh proof and explicit rebase. Rate-limit **every** route per owner/device + project with integer `Retry-After` 1..60; admitted page leases additionally have the durable one-429-per-page guarantee above. Reject large POSTs before parse and return no 3xx on authenticated APIs.
